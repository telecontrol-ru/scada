# Сервер
{:.no_toc}

* TOC
{:toc}

Сервер ОИК является центральным компонентом системы. Он выполняет сбор данных с оборудования, обработку данных реального времени, архивирование, регистрацию событий и обслуживание клиентских подключений. Сервер работает под Windows (в виде системных служб или в консольном режиме) и Linux (в том числе в Docker-контейнере).

Сервер состоит из отдельных процессов: `scada-config`, `scada-proxy`, `scada-historian`, `scada-filesystem`, процессов протокольного уровня и др. Их назначение и типовые установки описаны в разделе [Состав Сервера]({{ '/architecture/' | relative_url }}#tiers). Все процессы запускаются и настраиваются одинаково, поэтому ниже под «Сервером» понимается любой из них, а под `server.json` — файл параметров конкретного процесса.

## Запуск и управление

### Службы Windows {#services}

Каждый процесс Сервера устанавливается отдельной системной службой — *Telecontrol SCADA Config*, *Telecontrol SCADA Proxy*, *Telecontrol SCADA Historian*, *Telecontrol SCADA IEC 104* и т.д. (полный список — в разделе [Состав Сервера]({{ '/architecture/' | relative_url }}#tiers)). Службы регистрирует [`scada-setup`](#scada-setup); они работают от имени учетной записи SYSTEM и запускаются автоматически при загрузке Windows. Остановить и запустить все службы компьютера в правильном порядке можно командами `scada-setup stop` и `scada-setup start`; отдельную службу — стандартными средствами Windows (Панель управления — Службы).

Если на компьютере есть *Telecontrol SCADA Config*, остальные его службы зависят от нее, а *Telecontrol SCADA Proxy* — также от *Telecontrol SCADA Filesystem*: Windows запускает зависящие службы после них, а остановить службу, пока работают зависящие от нее, Панель управления предлагает только вместе с ними.

**Восстановление после сбоя.** `scada-setup` настраивает для каждой службы
перезапуск при сбое: через 5 секунд после первого сбоя, через 10 секунд после
второго и через 60 секунд после последующих; счетчик сбоев сбрасывается через
сутки. Сбоем считается и завершение процесса с ненулевым кодом. Процесс,
остановившийся из-за отсутствия лицензии, завершается штатно и автоматически
не перезапускается — запустите его командой `scada-setup start`.

**ВНИМАНИЕ:** после перезапуска службы процесса протокольного уровня, в том
числе автоматического, запись в архив значений его объектов прекращается.
Перезапустите после этого службу *Telecontrol SCADA Historian* (смотрите
[Наблюдение за работой](#monitoring)).

### Настройка с помощью scada-setup {#scada-setup}

Под Windows процессы Сервера устанавливаются и настраиваются программой
`scada-setup` из состава установщика. Она сама создает файлы параметров
`%ProgramData%\Telecontrol\SCADA Server\<процесс>\server.json` из шаблонов,
конфигурационные БД, [сертификат Сервера](#opcua-certificate) и службы Windows. Папка процесса называется так же, как
процесс в параметре `--tiers` (`config`, `proxy`, `historian`, `iec104`…),
кроме `scada-filesystem`: его папка — `filestore`. Ключи `--install` /
`--uninstall` исполняемых файлов нужны только при ручной настройке без
`scada-setup`; службы, созданные `scada-setup`, ими не изменяйте и не
удаляйте — для этого есть `scada-setup apply` и `scada-setup remove`. Пошаговая установка
описана в разделе [Начало работы]({{ '/getting-started/' | relative_url }}).

| Команда | Действие | Права администратора |
|---|---|:-:|
| `scada-setup apply` | Создать файлы параметров, БД и, если его нет, [сертификат Сервера](#opcua-certificate), зарегистрировать и запустить службы процессов, на которые выдана лицензия | да |
| `scada-setup status` | Сведения о лицензии и состояние служб процессов | нет |
| `scada-setup start` / `stop` | Запуск / остановка служб компьютера в нужном порядке | да |
| `scada-setup remove [--purge-data]` | Остановить и удалить службы (с `--purge-data` — и данные процессов) | да |
| `scada-setup generate --output <папка>` | Только создать файлы параметров, для просмотра | нет |
| `scada-setup migrate [--execute]` | Перенести данные Сервера версии 2.5 — смотрите [Переход с версии 2.5](#upgrade-2-5) | с `--execute` — да |

Общие параметры: `--tiers <список>` (по умолчанию — процессы из лицензии),
`--central <адрес>` (обязателен на компьютере без `scada-config`),
`--advertise <адрес>` (адрес этого компьютера для других, если имя компьютера
не разрешается в сети), `--license <путь>` (по умолчанию
`%ProgramData%\Telecontrol\SCADA Server\license.json`),
`--svc-password <пароль>` (или переменная окружения `SCADA_SETUP_SVC_PASSWORD`),
`--root-password <пароль>` (или переменная окружения
`SCADA_SETUP_ROOT_PASSWORD`; [пароль root](#root-password), обязателен для
`apply` и `migrate --execute` на компьютере с `scada-config`, `scada-proxy`,
`scada-historian` или `scada-filesystem`), `--data-root`, `--install-root`.

`apply` можно выполнять повторно: он заново создает файлы параметров и
приводит службы к нужному состоянию, не трогая данные. Повторяйте в нем те же
`--tiers`, `--central` и `--advertise`, что и при установке: без `--tiers`
команда включает все процессы из лицензии.

**ВНИМАНИЕ:** `apply` создает каждый файл `server.json` заново из шаблона, и
**все** изменения, внесенные в него вручную, теряются — при каждом `apply`, в
том числе при каждом обновлении. Если вы изменили параметры вручную (например,
[проверку сертификатов клиентов OPC UA](#opcua-certificate)), сохраните копию
измененного файла и после каждого `apply` внесите изменения снова и
перезапустите процесс.

### Переход с версии 2.5 {#upgrade-2-5}

Версии 2.5 и ранее устанавливали один процесс — службу *Telecontrol SCADA
Server* — и хранили его данные в папках `Configuration`, `History` и
`FileSystem` внутри `%ProgramData%\Telecontrol\SCADA Server`. Команда
`scada-setup migrate` переносит эти данные в процессы версии 2.6:

| Данные версии 2.5 | Куда копируются |
|---|---|
| Конфигурация `Configuration\configuration.sqlite3` | В папку `Configuration` процессов `config`, `proxy` и `historian` |
| Пароли пользователей `Configuration\password.dat` | Туда же, рядом с каждой копией конфигурации |
| Архивы `History` | `historian\History` |
| Файлы мнемосхем `FileSystem` | `filestore\FileSystem` |

Все пути указаны относительно `%ProgramData%\Telecontrol\SCADA Server`; если в
`server.json` версии 2.5 были заданы другие папки, команда берет их оттуда.
Конфигурация копируется в три процесса, потому что каждый работает со своей
копией: `scada-config` передает ее процессам протокольного уровня,
`scada-proxy` проверяет по ней имена и пароли пользователей Клиента,
`scada-historian` берет из нее список исторических БД и назначение объектов.

**Папки версии 2.5 только читаются**: команда ничего в них не изменяет и не
удаляет. Это важно, потому что при первом запуске процессы 2.6 преобразуют
свои копии в новый формат, после которого версия 2.5 работать с ними уже не
сможет. Удалите старые папки сами, когда убедитесь, что обновленная система
работает.

Порядок перехода — на компьютере, где работал Сервер 2.5:

1. Получите лицензию версии 2.6 (файл `license.json`) в ООО «Телеконтроль» и
   положите ее в `%ProgramData%\Telecontrol\SCADA Server\license.json`.
   Аппаратный ключ HASP или Guardant версией 2.6 не используется.
2. Сделайте резервную копию всей папки
   `%ProgramData%\Telecontrol\SCADA Server`.
3. Установите пакет версии 2.6:

   ```bat
   msiexec /i telecontrol-scada-<версия>.msi /qn
   ```

   Установщик заменяет программу версии 2.5 и обычно сам удаляет ее службу;
   данные остаются на месте.
4. Посмотрите, что будет сделано (команда ничего не меняет):

   ```bat
   scada-setup migrate
   ```

   Она перечисляет, что и куда будет скопировано, сколько места для этого
   нужно, какие настройки версии 2.5 не переносятся и что мешает переходу.
5. Выполните переход в командной строке с правами администратора:

   ```bat
   scada-setup migrate --execute --svc-password <пароль> --root-password <пароль root>
   ```

   Команда останавливает и удаляет службу *Telecontrol SCADA Server*, если
   она еще осталась, копирует данные и затем выполняет `scada-setup apply`:
   создает файлы параметров и, если его еще нет,
   [сертификат Сервера](#opcua-certificate), регистрирует и запускает службы
   процессов. Пароли пользователей переносятся, а пароль `root` версии 2.5 —
   и заданный параметром `security.rootPassword`, и измененный из Клиента —
   при первом запуске процессов 2.6 заменяется [паролем root](#root-password)
   из `--root-password`.
6. Подключитесь Клиентом (порт 2000, как и раньше) под учетной записью
   пользователя и проверьте объекты, архивы и мнемосхемы.

Переход не выполняется, а команда объясняет причину, если:

* конфигурация версии 2.5 хранится не в SQLite (например, в PostgreSQL);
* в версии 2.5 есть пользователь с идентификатором 100 — он занят служебной
  учетной записью `svc`. Создайте в версии 2.5 такого же пользователя под
  другим именем, удалите старого и повторите переход;
* на этом компьютере не выбран ни один из процессов `config`, `proxy` и
  `historian`;
* данные уже были перенесены (папки назначения существуют — команда никогда
  их не перезаписывает);
* на диске недостаточно места.

Параметры `--from <папка>` (папка с `server.json` версии 2.5, если это не
`%ProgramData%\Telecontrol\SCADA Server`) и `--from-exe-dir <папка>` (папка
программы версии 2.5 — нужна, только если `server.json` не задавал папку
данных и она находилась рядом с программой) используются редко.

Если в версии 2.5 были включены клиент OPC или интеграция с ОИК Видикон, в
версии 2.6 это отдельные процессы `scada-opc` и `scada-vidicon`: лицензия
должна их включать. Команда `migrate` напоминает об этом в списке непереносимых
настроек.

### Консольный режим {#console}

Для диагностики процесс Сервера можно запустить в консольном окне: он работает
так же, как служба, и выводит журнал на экран. Пиктограммы для этого
установщик не создает.

1. Остановите службу процесса (например, *Telecontrol SCADA IEC 104*):
   процесс и его служба не могут работать одновременно — они используют одни
   и те же порты и файлы.
2. Откройте командную строку с правами администратора: без них процесс не
   может прочитать закрытый ключ [сертификата Сервера](#opcua-certificate) и
   не запускается.
3. Задайте пароли, которые служба получает от `scada-setup`, и запустите
   процесс с его файлом параметров:

   ```bat
   set SCADA_SVC_PASSWORD=<пароль svc>
   set SCADA_ROOT_PASSWORD=<пароль root>
   "C:\Program Files\Telecontrol SCADA\bin\scada-iec104.exe" --param "%ProgramData%\Telecontrol\SCADA Server\iec104\server.json"
   ```

   Имя исполняемого файла — `scada-<процесс>.exe`, папка файла параметров —
   `config`, `proxy`, `historian`, `filestore` (для `scada-filesystem`),
   `modbus`, `iec104`, `iec61850`, `opc` или `vidicon`.
4. Для завершения закройте окно или нажмите *Ctrl+C*, затем снова запустите
   службу: `scada-setup start`.

**ВНИМАНИЕ:** если запустить `scada-config`, `scada-proxy`, `scada-historian`
или `scada-filesystem` без переменной `SCADA_ROOT_PASSWORD`, процесс
**установит учетной записи `root` пустой пароль** — их файлы параметров
содержат `"rootPassword": "$ENV{SCADA_ROOT_PASSWORD}"`, а заданный пароль
записывается при каждом запуске (смотрите [Пароль root](#root-password)).
Задавайте в `SCADA_ROOT_PASSWORD` тот же пароль, что и в `apply`. Без
`SCADA_SVC_PASSWORD` процесс не сможет подключиться к остальным процессам.
Процессам протокольного уровня `SCADA_ROOT_PASSWORD` не нужен.

### Параметры командной строки

| Параметр | Описание |
|---|---|
| `--install` | Установить Сервер как службу Windows (только при ручной настройке без `scada-setup`) |
| `--uninstall` | Удалить службу Windows (только при ручной настройке без `scada-setup`) |
| `--service` | Запуск в режиме службы (используется системой) |
| `--param <путь>` | Указать путь к файлу параметров. По умолчанию на Windows — `%ProgramData%\Telecontrol\SCADA <процесс>\<имя>.json` (например, `%ProgramData%\Telecontrol\SCADA IEC 104\scada-iec104.json`), на Linux — `<имя>.json` в папке `data` рядом с папкой исполняемого файла |
| `--name <имя>` | Задать имя службы Windows вместо стандартного — позволяет установить на одном компьютере несколько служб одного процесса |
| `--display-name <имя>` | Задать отображаемое имя службы и заголовок консольного окна |

Процессы, установленные `scada-setup`, запускаются с `--param`, указывающим на
`%ProgramData%\Telecontrol\SCADA Server\<папка процесса>\server.json`.

### Развертывание под Linux {#linux}

Серверный компонент поддерживает работу под Linux. Графический клиент под Linux не поддерживается.

#### Запуск из архива

Распакуйте архив дистрибутива и запустите исполняемые файлы нужных процессов (`scada-config`, `scada-iec104` и т.д.). Каждый процесс читает свой файл параметров `data/<имя>.json` (путь к папке `data` отсчитывается от папки исполняемого файла: `<папка программы>/../data`) или файл, указанный параметром `--param`.

#### Развертывание в Docker

Для контейнерного развертывания используется единый Docker-образ для всех процессов. Процесс, который запускает контейнер, выбирается переменной окружения `ROLE` (`config`, `proxy`, `historian`, `filesystem`, `modbus`, `iec104`, `iec61850`); файл параметров процесса монтируется в контейнер как `/etc/scada/<ROLE>.json`. Клиентские подключения принимает контейнер `proxy` на порту 2000.

В файле параметров поддерживается подстановка переменных окружения в формате `$ENV{VARIABLE_NAME}`, что позволяет задавать параметры (например, строку подключения к PostgreSQL или [пароль root](#root-password)) через переменные окружения контейнера. Неопределенная переменная заменяется пустой строкой.

## Лицензирование {#licensing}

Каждому процессу Сервера нужен подписанный файл лицензии. В лицензии указаны
срок действия и приобретенные процессы; процесс, не названный в лицензии,
работать не будет. Аппаратный ключ не используется.

Параметры задаются в блоке `license` файла параметров:

```json
"license": {
    "file": "C:\\ProgramData\\Telecontrol\\license.json",
    "require_gcp_binding": false
}
```

| Параметр | По умолчанию | Описание |
|---|---|---|
| `file` | `license.json` | Путь к файлу лицензии. Относительный путь отсчитывается от рабочей папки процесса, поэтому надежнее указывать абсолютный. Если параметр не задан, используется переменная окружения `SCADA_SERVER_LICENSE_FILE` |
| `require_gcp_binding` | `true` | Проверять привязку лицензии к виртуальной машине Google Cloud. **Вне Google Cloud задайте `false`**, иначе лицензия не может быть проверена. Если параметр не задан, используется переменная окружения `SCADA_SERVER_LICENSE_REQUIRE_GCP_BINDING` |

Файлы параметров, созданные [`scada-setup`](#scada-setup), уже содержат путь `%ProgramData%\Telecontrol\SCADA Server\license.json` (или заданный ключом `--license`) и `"require_gcp_binding": false`.

Лицензия проверяется при запуске и затем каждые 5 секунд:

* **Нет действительной лицензии** или она не включает этот процесс — процесс
  останавливается. Причина записывается в журнал. Так же процесс поступает,
  если в момент проверки файла нет или он записан не полностью. Служба при
  этом завершается штатно, и Windows ее **не перезапускает** — после
  исправления файла запустите процессы командой `scada-setup start`.
* **Лицензию не удалось проверить** (например, не ответил сервер метаданных
  Google Cloud) — процесс продолжает работать, но не обслуживает запросы, пока
  проверка не завершится.
* **Срок лицензии истек** — процесс продолжает работать, но отклоняет запросы.
  После замены файла лицензии обслуживание возобновляется без перезапуска.

Срок действия лицензии показывает команда `scada-setup status`. В последние
30 дней Сервер также ежедневно выдает системное событие об окончании срока, но
его видно только в Клиенте.

Заменяйте файл лицензии за один шаг: скопируйте новый файл в ту же папку под
временным именем и переименуйте его в `license.json` поверх старого (`move /y`)
— смотрите [Лицензия]({{ '/getting-started/' | relative_url }}#license).

Версии 2.5 и ранее использовали аппаратный ключ HASP или Guardant и без него
работали в демонстрационном режиме 2 часа.

## Конфигурационная БД

Для хранения конфигурации используется база данных в папке, заданной параметром `configuration.dir` файла параметров процесса. Удобно указывать `${DIR_PARAM}/Configuration` — папку рядом с файлом параметров, как в примере ниже. Если параметр не задан, БД создается в папке исполняемого файла.

### SQLite

По умолчанию используется встроенная БД [SQLite](https://www.sqlite.org/index.html), не требующая установки дополнительного ПО:

```json
"configuration": {
    "driver": "SQLite",
    "dir": "${DIR_PARAM}/Configuration"
}
```

### PostgreSQL

Для распределенных установок и повышенных требований к надежности поддерживается [PostgreSQL](https://www.postgresql.org/):

```json
"configuration": {
    "driver": "PostgreSQL",
    "connection-string": "postgresql://user:password@localhost:5432/scada"
}
```

При использовании PostgreSQL требуется предварительно установить и настроить сервер PostgreSQL.

### Миграция конфигурационной БД GigaBASE {#migration}

Поддержка GigaBASE была удалена начиная с версии 2.1. Для импорта старых конфигураций GigaBASE используйте утилиту администрации версии 2.0.

Утилита не публикуется на странице выпусков; для ее получения обратитесь в ООО «Телеконтроль» (mail@telecontrol.ru). Распакуйте архив ZIP и запустите из распакованной директории:

```batch
admin export --source-driver=GigaBASE "--source=c:\ProgramData\Telecontrol\SCADA Server\Configuration" --target-driver=SQLite "--target=c:\ProgramData\Telecontrol\SCADA Server\Configuration"
```

Эта команда создаст файл конфигурации SQLite `configuration.sqlite3` в директории `c:\ProgramData\Telecontrol\SCADA Server\Configuration`. Все содержимое старой конфигурации будет импортировано в новую конфигурацию.

Для использования новой конфигурации нужно обновить параметры сервера. Откройте файл `server.json` и измените параметр `configuration.driver` с `GigaBASE` на `SQLite`. Если такой параметр отсутствует, его нужно добавить.

## Исторические БД {#history}

Исторические БД создаются в формате [SQLite](https://www.sqlite.org/index.html).

Для хранения событий аудита и последних значений объектов используется системная историческая БД.

Для хранения событий и изменений значений параметров используются пользовательские исторические БД. Допустимо создание нескольких пользовательских исторических БД. Сервер автоматически создает и удаляет необходимые файлы на диске при создании и удалении БД.

Исторические БД ведет процесс `scada-historian`. Местоположение БД определяется параметром `history.dir` его файла параметров; `scada-setup` задает папку `%ProgramData%\Telecontrol\SCADA Server\historian\History`. (Сервер версии 2.5 хранил их в `%ProgramData%\Telecontrol\SCADA Server\History`; при [переходе с версии 2.5](#upgrade-2-5) они копируются в новую папку.)

Для каждой БД создается собственная подпапка с числовым идентификатором БД. Исключением является фиксированное имя `System` системной БД. Каждому объекту может быть назначена одна БД. При удалении объекта все связанные с ним данные удаляются из БД. При переназначении БД объекту связанные с ним данные удаляются из предыдущей БД.

Историческим БД задается глубина хранения данных. Сервер автоматически выполняет очистку БД в соответствии с ее глубиной.

### Оценка требуемого дискового пространства

Новые БД создаются со стандартным для SQLite размером страницы 4 Кб; БД, перенесенные из прежних версий, сохраняют свой. Допустимые размеры смотрите в [характеристиках SQLite](https://sqlite.org/limits.html).

Размер записи одного [Объекта]({{ '/architecture/' | relative_url }}#data-items) составляет менее 100 Байт.

Таким образом, ожидаемый размер БД в Мб можно вычислить как:
`size = freq * depth / 10000`, где:
- `size` - ожидаемый размер БД в Мб;
- `freq` - частота изменений в день;
- `depth` - глубина (в днях).

Либо, при известном объеме доступного дискового пространства, можно вычислить максимальную глубину в днях:
`depth = size * 10000 / freq`.

### Работа с БД SQLite

Данный пункт описывает дополнительные возможности администрирования и диагностики. Так как сервер выполняет обслуживание БД в автоматическом режиме, ознакомление с данным пунктом не требуется.

Удобный графический интерфейс предоставляет бесплатная утилита [SQLiteStudio](https://sqlitestudio.pl/).

Для прямого доступа к БД можно использовать утилиту командной строки `sqlite3`. В установку версии 2.6 она не входит (версии 2.5 и ранее ее устанавливали); загрузите ее со [страницы загрузок SQLite](https://sqlite.org/download.html). Файл БД называется `history` и лежит в папке БД. Перейдите в эту папку и выполните команду

```batch
sqlite3 history
```

Открывайте для записи только БД остановленного процесса (`scada-setup stop`).

Утилита позволяет выполнять запросы SQL и ряд специальных команд. Для информации о списке допустимых команд смотрите [документацию SQLite](https://sqlite.org/cli.html).

#### Примеры

Размер страницы БД:

```SQL
sqlite> pragma page_size;
4096
```

Перечень таблиц: значения параметров (`timed_data`), последние значения
объектов (`items_info`) и по таблице на каждый тип событий:

```SQL
sqlite> .tables
AuditActivateSessionEventType  OperatorActionAuditEventType
AuditUpdateMethodEventType     SystemEventType
DeviceWatchEventType           items_info
ItemAlarmEventType             timed_data
```

В БД, перенесенной из прежних версий, может быть также таблица
`events_v1_backup` — это исходная таблица событий старого формата, данные
которой уже перенесены в `SystemEventType`.

Схема таблицы системных событий:

```SQL
sqlite> .schema SystemEventType
CREATE TABLE SystemEventType(EventID INTEGER PRIMARY KEY NOT NULL, Time INTEGER NOT NULL, ReceiveTime INTEGER NOT NULL, ChangeMask INTEGER, Severity INTEGER, NodeNS INTEGER NOT NULL, NodeID INTEGER NOT NULL, UserID INTEGER, Value FLOAT, Qualifier INTEGER, Message TEXT, Acked BOOLEAN NOT NULL, AckTime INTEGER, AckUserID INTEGER, SourceName TEXT, MessageLocale TEXT, SourceNameLocale TEXT);
CREATE INDEX SystemEventType_TimeIndex ON SystemEventType(Time);
CREATE INDEX SystemEventType_NodeIndex ON SystemEventType(NodeNS, NodeID);
```

Количество системных событий в архиве:

```SQL
sqlite> select count(*) from SystemEventType;
86
```

## Серверная файловая система {#filesystem}

Серверная файловая система позволяет хранить файлы мнемосхем на Сервере. Таким образом, доступ к мнемосхемам будет предоставлен всем Клиентам, избавляя их от необходимости ручной синхронизации при обновлении файлов.

Серверную файловую систему ведет процесс `scada-filesystem`. В файле параметров, который создает `scada-setup`, она уже включена. При ручной настройке включите ее параметром `filesystem.enabled` в файле `server.json` процесса:

```json
"filesystem": {
    "enabled": true,
    "dir": "${DIR_PARAM}/FileSystem"
}
```

Файлы мнемосхем размещаются в папке, указанной в параметре `dir`; `scada-setup` задает папку `%ProgramData%\Telecontrol\SCADA Server\filestore\FileSystem`. (Сервер версии 2.5 хранил их в `%ProgramData%\Telecontrol\SCADA Server\FileSystem`; при [переходе с версии 2.5](#upgrade-2-5) они копируются в новую папку.) Управление файлами выполняется из [панели файлов]({{ '/client/' | relative_url }}) Клиента.

## Логирование {#logging}

Каждый процесс ведет журнал работы в текстовых файлах с именами вида
`scada-<процесс>_<дата>_<время>-<номер>.log` (например,
`scada-iec104_2026-10-04_08-00-00-0.log`). У процессов, установленных
`scada-setup`, журналы находятся в папке `Logs` папки процесса:
`%ProgramData%\Telecontrol\SCADA Server\<папка процесса>\Logs`. Параметры
логирования:

| Параметр | По умолчанию | Описание |
|---|---|---|
| `log.dir` | `%ProgramData%\Telecontrol\SCADA Server\logs` (на Linux — `Telecontrol/SCADA Server/logs` относительно рабочей папки процесса) | Папка файлов журнала |
| `log.max_file_size` | 10 | Максимальный размер одного файла (Мб) |
| `log.max_total_size` | 100 | Максимальный общий размер всех файлов (Мб) |
| `log.max_count` | 1000 | Максимальное количество файлов |
| `log.console_severity` | — | Наименьший уровень сообщений, выводимых **на экран** в [консольном режиме](#console) или в вывод контейнера: `Trace`, `Debug`, `Info`, `Warning`, `Error` или `Critical`. На файлы журнала не влияет |

Новый файл создается при достижении максимального размера и каждые сутки в
полночь. При превышении общего размера или количества файлов старые файлы
удаляются автоматически. Уровень сообщений, записываемых в файлы, не
настраивается.

## Наблюдение за работой {#monitoring}

* **Состояние служб и лицензии** — команда `scada-setup status` на каждом
  компьютере: срок действия лицензии, процессы, на которые она выдана, и
  состояние службы каждого процесса.
* **Журналы процессов** — смотрите [Логирование](#logging). Причины остановки
  процесса (лицензия, сертификат, файл параметров) записываются в журнал.
* **Запись в архив** — окно Клиента *Дополнительно — Базы данных* показывает
  для каждого архива количество записанных измерений и очередь записи
  (смотрите [Базы данных]({{ '/client/workbench/' | relative_url }}#historical-db)).
  Если количество записанных измерений перестало расти, хотя значения
  объектов меняются, перезапустите службу *Telecontrol SCADA Historian*:
  после перезапуска службы процесса протокольного уровня, в том числе
  автоматического после сбоя, запись значений его объектов в архив
  прекращается до перезапуска *Telecontrol SCADA Historian*.

## Клиентские подключения {#sessions}

Параметр `sessions` определяет адреса и порты для приема клиентских подключений. По умолчанию Сервер принимает подключения на всех сетевых интерфейсах (`0.0.0.0`) на порту `2000`.

```json
"sessions": [
    "tcp;passive;host=0.0.0.0;port=2000"
]
```

Допускается задание нескольких точек подключения, например для разных сетевых интерфейсов или портов.

## Пароль root {#root-password}

Встроенная учетная запись `root` имеет все права и существует всегда, независимо от содержимого конфигурации. Ее пароль задается параметром `security.rootPassword`:

```json
"security": {
    "rootPassword": "$ENV{SCADA_ROOT_PASSWORD}"
}
```

**ВНИМАНИЕ:** если параметр не задан, при первом запуске `root` получает пустой пароль и Сервер принимает вход `root` без пароля (в журнал выводится предупреждение). Задайте пароль до того, как Сервер станет доступен по сети.

Заданное значение имеет приоритет: оно записывается при каждом запуске и заменяет пароль, сохраненный ранее, в том числе измененный из Клиента. Чтобы пароль не хранился в файле открытым текстом, передавайте его через переменную окружения, как в примере выше.

**Под Windows пароль задает `scada-setup`**: файлы параметров, которые он создает для `scada-config`, `scada-proxy`, `scada-historian` и `scada-filesystem`, содержат `"rootPassword": "$ENV{SCADA_ROOT_PASSWORD}"`, а значение переменной `scada-setup apply` берет из параметра `--root-password` (или переменной окружения `SCADA_SETUP_ROOT_PASSWORD`) и сохраняет в параметрах служб Windows этих процессов. На компьютере с одним из этих процессов `apply` без пароля не выполняется. Чтобы сменить пароль `root`, выполните `apply` с новым значением; править созданные файлы параметров не нужно — при следующем `apply` они создаются заново.

Параметр задается **каждому** процессу, который хранит конфигурацию в собственной базе данных, — у каждого из них своя учетная запись `root`: это `scada-config`, `scada-proxy`, `scada-historian` и `scada-filesystem`. Процессы протокольного уровня получают конфигурацию от `scada-config` и этот параметр не используют (об этом выводится сообщение в журнал).

**ВНИМАНИЕ:** переменную `SCADA_ROOT_PASSWORD` процесс получает от службы. При запуске такого процесса вне службы (например, в [консольном режиме](#console)) без этой переменной `root` получит пустой пароль.

## Сервер OPC UA {#opcua}

Сервер может предоставлять данные внешним системам по протоколу [OPC UA](https://opcfoundation.org/about/opc-technologies/opc-ua/). При включении OPC UA внешние клиенты получают доступ к адресному пространству Сервера ОИК: объектам, устройствам, текущим и историческим данным.

В установке, созданной `scada-setup`, OPC UA включен у каждого процесса (порты 4840–4848, смотрите [Настройка сети]({{ '/getting-started/' | relative_url }}#network)): по нему процессы обмениваются данными между собой.

**ВНИМАНИЕ:** открывайте порты OPC UA только для компьютеров объекта.
Процессы регистрируются у `scada-proxy` и `scada-config` без проверки
подлинности, анонимный вход предлагается всегда, а сертификаты клиентов по
умолчанию не проверяются. Если к Серверу должна подключаться внешняя система,
разрешите в брандмауэре доступ к порту 4840 только с ее адреса и включите
[проверку сертификатов клиентов](#opcua-certificate).

Для включения установите параметр `opcua.enabled` в значение `true`:

```json
"opcua": {
    "enabled": true,
    "url": "opc.tcp://localhost:4840",
    "server_private_key": "${DIR_PARAM}/Certificates/ServerPrivateKey.pem",
    "server_certificate": "${DIR_PARAM}/Certificates/ServerCertificate.pem",
    "trace": "none"
}
```

| Параметр | Описание |
|---|---|
| `enabled` | Включить сервер OPC UA |
| `url` | Адрес и порт сервера OPC UA |
| `server_private_key` | Путь к файлу закрытого ключа (PEM) |
| `server_certificate` | Путь к файлу сертификата (PEM) |
| `trace` | Уровень диагностики: none, error, warning, info, debug, all |

### Сертификат Сервера {#opcua-certificate}

Для защищенных соединений (политика Basic256Sha256, режим «Подпись и
шифрование») процессу нужны закрытый ключ и сертификат в формате PEM, заданные
параметрами `server_private_key` и `server_certificate`:

* ключ RSA (рекомендуется 2048 бит) **без пароля**;
* если параметры не заданы, процесс предлагает только незащищенные
  соединения (политика None);
* **если параметры заданы, а файлов нет или их не удается прочитать,
  процесс не запускается** — в журнал выводится `Can't open file` или
  `Failed to parse OPC UA server certificate PEM`.

Файлы параметров, созданные [`scada-setup`](#scada-setup), ссылаются на
`C:\Program Files\Telecontrol SCADA\data\Certificates\ServerCertificate.pem`
и `ServerPrivateKey.pem`. Установщик этих файлов не содержит — **их создает
`scada-setup apply`, если их там еще нет**:

* ключ RSA 2048 бит без пароля и самоподписанный сертификат SHA-256 сроком
  на 5 лет;
* в сертификат записываются идентификаторы (ApplicationUri) всех процессов,
  которые `apply` включает на этом компьютере, имя компьютера, `localhost`,
  `127.0.0.1` и адрес из параметра `--advertise`, если он задан;
* доступ к файлу ключа есть только у учетной записи SYSTEM, от имени которой
  работают службы, и у администраторов.

Одна пара служит всем процессам компьютера. Существующие файлы `apply` никогда
не заменяет. Если после создания пары на компьютере включен процесс, которого
в сертификате нет, `apply` выводит предупреждение с его идентификатором:
сторонние клиенты OPC UA, проверяющие сертификат, могут отказаться
подключаться к этому процессу. Если есть только один из двух файлов, `apply`
останавливается с сообщением о недостающем файле.

**Чтобы заменить сертификат** — выпустить новый, включить в него добавленные
процессы или поставить сертификат своего удостоверяющего центра:

1. Остановите процессы: `scada-setup stop`.
2. Удалите оба файла из `C:\Program Files\Telecontrol SCADA\data\Certificates`
   или положите вместо них свою пару (ключ в формате PEM без пароля).
3. Выполните `scada-setup apply` с теми же параметрами, что и при установке:
   недостающая пара будет создана заново, процессы запустятся.

Свою самоподписанную пару можно также создать программой
[OpenSSL](https://www.openssl.org/) (в Windows она не входит в состав системы;
ее устанавливают, например, вместе с Git для Windows). Сохраните в файл
`cert.cnf`:

```ini
[req]
distinguished_name = dn
x509_extensions = v3
prompt = no

[dn]
O = Telecontrol
CN = Telecontrol SCADA Server

[v3]
basicConstraints = critical, CA:TRUE
keyUsage = critical, digitalSignature, nonRepudiation, keyEncipherment, dataEncipherment, keyCertSign
extendedKeyUsage = serverAuth, clientAuth
subjectKeyIdentifier = hash
subjectAltName = @san

[san]
URI.1 = urn:telecontrol:scada:server
URI.2 = urn:SCADA-HOST:scada:historian
DNS.1 = SCADA-HOST
DNS.2 = localhost
IP.1 = 127.0.0.1
```

и выполните:

```bat
openssl req -x509 -nodes -newkey rsa:2048 -sha256 -days 1826 ^
    -keyout ServerPrivateKey.pem -out ServerCertificate.pem -config cert.cnf
```

В разделе `[san]` замените `SCADA-HOST` именем компьютера и перечислите
идентификаторы (ApplicationUri) всех процессов, работающих на нем:
`urn:telecontrol:scada:server` для `scada-config` и `scada-proxy`,
`urn:<имя компьютера>:scada:<процесс>` для остальных (например
`urn:SCADA-HOST:scada:iec104`). Спецификация OPC UA требует, чтобы сертификат
содержал идентификатор приложения, и сторонние клиенты OPC UA это проверяют.
Скопируйте оба файла в папку, на которую ссылаются параметры, и ограничьте
доступ к файлу ключа.

Проверка сертификатов **клиентов** по умолчанию выключена: Сервер принимает
любой клиентский сертификат. Чтобы принимать только доверенные, задайте папки
в блоке `opcua` файла параметров:

| Параметр | Описание |
|---|---|
| `trusted_certificates_dir` | Доверенные сертификаты клиентов (PEM или DER); клиент принимается, если его сертификат есть в этой папке |
| `issuer_certificates_dir` | Сертификаты удостоверяющих центров; принимается клиент, чей сертификат ими подписан |
| `crl_dir` | Списки отзыва для удостоверяющих центров |
| `rejected_certificates_dir` | Сюда записываются отклоненные сертификаты клиентов — их можно перенести в доверенные |

Дополнительные ограничения задаются в блоке `opcua.security`:
`"allow_none": false` запрещает незащищенные соединения,
`"require_encryption_for_password": true` запрещает передачу пароля без
шифрования, `"require_trusted_client_cert": true` требует доверенный сертификат
клиента. Анонимный вход предлагается всегда. Настольный Клиент сертификат
Сервера не проверяет.

**ВНИМАНИЕ:** `scada-setup` этих параметров не задает, а каждый
`scada-setup apply` (в том числе при обновлении) создает файлы параметров
заново, и добавленные вручную параметры теряются. Сохраните копию измененных
файлов и после каждого `apply` внесите изменения снова и перезапустите
процессы.

## Клиент OPC (Windows) {#opc-classic}

На Windows Сервер может подключаться к внешним OPC-серверам по протоколу OPC DA (Classic OPC). При включении этой функции теги внешних OPC-серверов отображаются в адресном пространстве Сервера ОИК и могут быть привязаны к объектам.

```json
"opc": {
    "client": {
        "enabled": true
    }
}
```

Функция доступна только на Windows.

## Интеграция с ОИК Видикон {#vidicon}

Сервер поддерживает интеграцию с системой ОИК Видикон для миграции существующих проектов. При включении Сервер импортирует объекты из конфигурации Видикон в своё адресное пространство.

```json
"vidicon": {
    "enabled": true
}
```

Функция доступна только на Windows.

## Резервное копирование {#backup}

На каждом компьютере с процессами Сервера копируйте:

* папку `%ProgramData%\Telecontrol\SCADA Server` целиком — у каждого процесса
  в ней своя папка с файлом параметров, базами данных и журналами, а рядом
  лежит файл лицензии `license.json`;
* папку `C:\Program Files\Telecontrol SCADA\data\Certificates` —
  [сертификат Сервера](#opcua-certificate) и его закрытый ключ. Храните копию
  ключа так же надежно, как пароли.

Копируйте только при **остановленных процессах этого компьютера**: копия
файлов работающих баз данных может оказаться несогласованной.

```bat
scada-setup stop
rem скопируйте %ProgramData%\Telecontrol\SCADA Server
rem и C:\Program Files\Telecontrol SCADA\data\Certificates
scada-setup start
```

Для восстановления понадобятся также пароль `svc`, пароль `root` и параметры
`--tiers`, `--central` и `--advertise`, с которыми на этом компьютере
выполнялся `scada-setup apply`; в резервную копию они не попадают.

### Резервное копирование конфигурации

Конфигурационные БД SQLite хранятся в папках `Configuration` процессов
`config`, `proxy`, `historian` и `filestore`. Основная конфигурация — у
`scada-config` (`config\Configuration`); по копии `scada-proxy`
(`proxy\Configuration`) проверяются имена и пароли пользователей Клиента.

При использовании PostgreSQL используйте стандартные средства резервного копирования PostgreSQL (`pg_dump`).

### Резервное копирование архивов

Исторические БД хранятся в папке `historian\History`, файлы мнемосхем — в
`filestore\FileSystem`.

В версии 2.5 и ранее эти данные находились в папках `Configuration`, `History`
и `FileSystem` непосредственно в `%ProgramData%\Telecontrol\SCADA Server`.
После [перехода с версии 2.5](#upgrade-2-5) они остаются на месте, но
процессами 2.6 уже не используются.

### Восстановление {#restore}

На том же компьютере:

1. Остановите процессы: `scada-setup stop`.
2. Верните на место папку `%ProgramData%\Telecontrol\SCADA Server` (и, если
   ее нет, папку `Certificates`) из резервной копии.
3. Запустите процессы: `scada-setup start`.
4. Проверьте результат: `scada-setup status`.

На новом или переустановленном компьютере:

1. Установите пакет **той же версии**, что и в резервной копии.
2. Верните папку `%ProgramData%\Telecontrol\SCADA Server` и папку
   `C:\Program Files\Telecontrol SCADA\data\Certificates` из резервной копии.
   Ограничьте доступ к файлу `ServerPrivateKey.pem` учетной записью SYSTEM и
   администраторами: при копировании он получает права папки.
3. В командной строке с правами администратора выполните `scada-setup apply`
   с теми же `--tiers`, `--central` и `--advertise`, что и раньше, **тем же
   паролем `svc`** и паролем `root`. Пароль `svc` хранится в восстановленных
   базах, и с другим паролем процессы не смогут подключиться друг к другу.
   `apply` регистрирует службы и запускает их; восстановленные базы и
   сертификат он сохраняет.
4. Проверьте результат: `scada-setup status`.

Без папки `Certificates` `apply` создаст новый сертификат; сторонние клиенты
OPC UA, доверявшие старому, придется настроить заново.

## Справочник параметров server.json {#parameters}

Системные параметры задаются в файле параметров процесса (`server.json` в тексте этого раздела). Расположение файла по умолчанию описано в параметре [`--param`](#параметры-командной-строки).

**ВНИМАНИЕ:** под Windows файлы параметров создает [`scada-setup`](#scada-setup), и каждый `scada-setup apply` — в том числе при каждом обновлении — создает их заново из шаблонов. **Любой параметр, измененный в `server.json` вручную, при этом теряется.** Если вы меняете параметры вручную, сохраните копию измененного файла и после каждого `apply` внесите изменения снова и перезапустите процесс.

В параметрах допускается использование переменных подстановки:

| Переменная | Описание |
|---|---|
| `${DIR_PARAM}` | Папка файла параметров |
| `${DIR_EXE}` | Папка исполняемого файла сервера |
| `${DIR_TEMP}` | Временная папка |
| `$ENV{ИМЯ}` | Значение переменной окружения `ИМЯ` (пустая строка, если она не задана) |

Пример файла параметров для ручной настройки (файлы, которые создает `scada-setup`, отличаются от него):

```json
{
    "configuration": {
        "driver": "SQLite",
        "dir": "${DIR_PARAM}/Configuration"
    },

    "history": {
        "dir": "${DIR_PARAM}/History"
    },

    "sessions": [
        "tcp;passive;host=0.0.0.0;port=2000"
    ],

    "opc": {
        "client": {
            "enabled": false
        }
    },

    "opcua": {
        "enabled": false,
        "url": "opc.tcp://localhost:4840",
        "server_private_key": "${DIR_PARAM}/Certificates/ServerPrivateKey.pem",
        "server_certificate": "${DIR_PARAM}/Certificates/ServerCertificate.pem",
        "trace": "none"
    },

    "filesystem": {
        "enabled": true,
        "dir": "${DIR_PARAM}/FileSystem"
    },

    "vidicon": {
        "enabled": false
    },

    "log": {
        "dir": "${DIR_PARAM}/Logs",
        "max_file_size": 10,
        "max_total_size": 100,
        "max_count": 1000
    },

    "thread_count": 1
}
```
