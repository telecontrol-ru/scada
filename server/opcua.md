## Сервер OPC UA {#opcua}

Сервер может предоставлять данные внешним системам по протоколу [OPC UA](https://opcfoundation.org/about/opc-technologies/opc-ua/). При включении OPC UA внешние клиенты получают доступ к адресному пространству Сервера ОИК: объектам, устройствам, текущим и историческим данным.

В установке, созданной `scada-setup`, OPC UA включен у каждого процесса (порты 4840–4848, смотрите [Настройка сети]({{ '/getting-started/' | relative_url }}#network)): по нему процессы обмениваются данными между собой.

Процессы подключаются друг к другу с шифрованием (политика Basic256Sha256,
режим «Подпись и шифрование») под учетной записью [`svc`]({{ '/server/security/' | relative_url }}#svc). Каждый
процесс, кроме `scada-config`, принимает только компьютеры, сертификат которых
выдан [удостоверяющим центром объекта](#opcua-site-ca) или перенесен в папку
`trusted`. `scada-config` (порт 4841) принимает защищенное соединение с
любым сертификатом: к нему обращается подключаемый компьютер, у которого
своего сертификата еще нет. Но без входа под учетной записью он ничего не
выдает, а сертификат объекта выдает только учетной записи `svc`: ни один
пользователь — ни `root`, ни администратор, ни пользователь с правом
«Настройка конфигурации» — получить его не может, и Клиент не может дать
такое право никому. Поэтому для подключения компьютера к объекту нужен пароль
`svc`; храните его так же, как пароль `root`.

Зарегистрироваться у `scada-proxy` и `scada-config` как процесс Сервера — после
чего `scada-proxy` обращается к нему как к процессу объекта — можно только с
сертификатом, выданным [удостоверяющим центром объекта](#opcua-site-ca), и
только под именем, которое в этом сертификате указано. Сертификат,
перенесенный в папку `trusted`, позволяет системе подключиться, но не
зарегистрироваться.
Незащищенных соединений (политика None) и анонимного входа не принимает ни
один процесс, в том числе порт 4840 `scada-proxy`, к которому подключаются
внешние системы, — если только на компьютере с `scada-proxy` `apply` не
выполнен с параметром `--allow-anonymous-opcua` (смотрите
[Подключение внешней системы](#opcua-external)). Пароль без шифрования не
принимает ни один процесс. Поэтому, как и прежде:

* открывайте порты OPC UA только для компьютеров объекта (смотрите
  [Настройка сети]({{ '/getting-started/' | relative_url }}#network));
* если к Серверу должна подключаться внешняя система, разрешите в
  брандмауэре доступ к порту 4840 (`scada-proxy`) только с ее адреса.

**ВНИМАНИЕ:** компьютер без `scada-config`, настроенный без
`--central-fingerprint`, получает самоподписанный сертификат, и на объекте с
удостоверяющим центром его процессы **вообще не могут подключиться** к
остальным: те отказывают в незащищенных соединениях и не принимают пароль без
шифрования, а его сертификату не доверяют. Поэтому `apply` с `--central` без
`--central-fingerprint` и без `--insecure-links` на компьютере, еще не
получившем сертификат от удостоверяющего центра, завершается ошибкой и ничего
не меняет.
Без шифрования, с паролем `svc` открытым текстом, работает только объект, все
компьютеры которого настроены с параметром
[`--insecure-links`]({{ '/server/setup/' | relative_url }}#scada-setup-options); на таком объекте защищает только
брандмауэр.

Для включения установите параметр `opcua.enabled` в значение `true`:

```json
"opcua": {
    "enabled": true,
    "url": "opc.tcp://localhost:4840",
    "server_private_key": "${DIR_PARAM}/Certificates/ServerPrivateKey.pem",
    "server_certificate": "${DIR_PARAM}/Certificates/ServerCertificate.pem",
    "trace": "none"
}
```

| Параметр | Описание |
|---|---|
| `enabled` | Включить сервер OPC UA |
| `url` | Адрес и порт сервера OPC UA |
| `server_private_key` | Путь к файлу закрытого ключа (PEM) |
| `server_certificate` | Путь к файлу сертификата (PEM) |
| `trace` | Уровень диагностики: none, error, warning, info, debug, all |

### Подключение внешней системы {#opcua-external}

Внешняя система OPC UA — система верхнего уровня, SCADA-система другого
производителя — подключается к порту 4840 `scada-proxy`. На объекте с
шифрованием (без `--insecure-links`) этот порт принимает только защищенные
соединения (режим «Подпись и шифрование») с входом по имени пользователя и
паролю:

1. Создайте для системы пользователя с нужными правами в окне Клиента
   [Пользователи]({{ '/client/workbench/' | relative_url }}#users).
2. Подключите систему к `opc.tcp://<компьютер с scada-proxy>:4840` в
   режиме «Подпись и шифрование» под этим пользователем. Первое подключение
   завершится отказом: сертификату системы `scada-proxy` не доверяет и
   записывает его в папку `data\Certificates\rejected` папки установки.
3. Перенесите этот файл в папку `data\Certificates\trusted` рядом с ней и
   перезапустите службу *Telecontrol SCADA Proxy* (Панель управления —
   Службы; под Linux — `systemctl restart scada-proxy`): список доверенных
   сертификатов процесс читает при запуске. Перезапуск на время прерывает
   связь Клиентов с Сервером.

**ВНИМАНИЕ:** папке `trusted` доверяют все процессы компьютера, поэтому
система с сертификатом в ней может установить защищенное соединение с любым из
них, а не только с портом 4840, — что она сможет делать дальше, решают права
пользователя, под которым она входит. Зарегистрироваться у `scada-proxy` или
`scada-config` как процесс Сервера она не может: это принимается только с
сертификатом, выданным удостоверяющим центром объекта. Переносите в `trusted`
только сертификаты систем, которые действительно должны подключаться;
открывайте такой системе в брандмауэре только порт 4840 и только с ее адреса;
удалите ее сертификат из `trusted`, когда система перестанет подключаться.

Если система не умеет ни шифрования, ни входа по имени пользователя — как
многие системы, подключавшиеся к Серверу 2.5, — выполните `apply` на
компьютере с `scada-proxy` с параметром
[`--allow-anonymous-opcua`]({{ '/server/setup/' | relative_url }}#scada-setup-options) вместе с остальными
параметрами компьютера. Тогда порт 4840 принимает и незащищенные соединения
(политика None), и анонимный вход: **любой, кто достиг порта, может
просматривать и читать адресное пространство Сервера** — объекты и их
значения, — но не изменять его и не управлять. Пароль без шифрования порт не
принимает и в этом случае. Разрешите в брандмауэре доступ к порту 4840
только с адреса этой системы. Остальные процессы анонимного входа не
принимают и с этим параметром. На объекте с `--insecure-links` порт 4840
принимает незащищенные соединения и анонимный вход и без него.

### Сертификат Сервера {#opcua-certificate}

Для защищенных соединений (политика Basic256Sha256, режим «Подпись и
шифрование») процессу нужны закрытый ключ и сертификат в формате PEM, заданные
параметрами `server_private_key` и `server_certificate`:

* ключ RSA (рекомендуется 2048 бит) **без пароля**;
* если параметры не заданы, процесс предлагает только незащищенные
  соединения (политика None);
* **если параметры заданы, а файлов нет или их не удается прочитать,
  процесс не запускается** — в журнал выводится `Can't open file` или
  `Failed to parse OPC UA server certificate PEM`.

Файлы параметров, созданные [`scada-setup`]({{ '/server/setup/' | relative_url }}), ссылаются на
`C:\Program Files\Telecontrol SCADA\data\Certificates\ServerCertificate.pem`
и `ServerPrivateKey.pem`. Установщик этих файлов не содержит — **их создает
`scada-setup apply`, если их там еще нет**:

* ключ RSA 2048 бит без пароля и сертификат SHA-256 сроком на 5 лет,
  выданный [удостоверяющим центром объекта](#opcua-site-ca) (самоподписанный
  — с `--insecure-links` или на компьютере, подключенном без
  `--central-fingerprint`);
* в сертификат записываются идентификаторы (ApplicationUri) всех процессов,
  которые `apply` включает на этом компьютере, имя компьютера, `localhost`,
  `127.0.0.1` и адрес из параметра `--advertise`, если он задан;
* доступ к файлу ключа есть только у учетной записи SYSTEM, от имени которой
  работают службы, и у администраторов.

Одна пара служит всем процессам компьютера. Существующие файлы `apply`
заменяет, только чтобы уйти от самоподписанной пары, когда удостоверяющий
центр объекта может выдать сертификат: старые файлы он оставляет рядом как
`ServerCertificate.pem.self-signed` и `ServerPrivateKey.pem.self-signed`.
Если после создания пары на компьютере включен процесс, которого в
сертификате нет, `apply` получает у удостоверяющего центра объекта новый
сертификат, в котором он есть, а старые файлы оставляет рядом как
`ServerCertificate.pem.previous-uris` и `ServerPrivateKey.pem.previous-uris`:
регистрацию процесса `scada-proxy` и `scada-config` принимают только под
идентификатором, указанным в его сертификате. Если выдать сертификат некому
(объект настроен с `--insecure-links`), `apply` вместо этого выводит
предупреждение с идентификатором процесса: такой процесс не сможет
зарегистрироваться, а сторонние клиенты OPC UA, проверяющие сертификат, могут
отказаться к нему подключаться. Если есть только один из двух файлов, `apply`
останавливается с сообщением о недостающем файле.

**Чтобы заменить сертификат** — выпустить новый, включить в него добавленные
процессы или поставить сертификат своего удостоверяющего центра:

1. Остановите процессы:
   `"C:\Program Files\Telecontrol SCADA\bin\scada-setup.exe" stop`.
2. Удалите оба файла из `C:\Program Files\Telecontrol SCADA\data\Certificates`
   или положите вместо них свою пару (ключ в формате PEM без пароля; доступ к
   нему ограничьте, как описано ниже).
3. Выполните `scada-setup apply` с теми же
   [параметрами компьютера]({{ '/server/setup/' | relative_url }}#scada-setup-options) и паролями, что и при
   установке, на компьютере без `scada-config` — вместе с
   `--central-fingerprint`: недостающая пара будет создана заново, процессы
   запустятся.

Свою самоподписанную пару можно также создать программой
[OpenSSL](https://www.openssl.org/) (в Windows она не входит в состав системы;
ее устанавливают, например, вместе с Git для Windows). Сохраните в файл
`cert.cnf`:

```ini
[req]
distinguished_name = dn
x509_extensions = v3
prompt = no

[dn]
O = Telecontrol
CN = Telecontrol SCADA Server

[v3]
basicConstraints = critical, CA:TRUE
keyUsage = critical, digitalSignature, nonRepudiation, keyEncipherment, dataEncipherment, keyCertSign
extendedKeyUsage = serverAuth, clientAuth
subjectKeyIdentifier = hash
subjectAltName = @san

[san]
URI.1 = urn:telecontrol:scada:server
URI.2 = urn:SCADA-HOST:scada:historian
DNS.1 = SCADA-HOST
DNS.2 = localhost
IP.1 = 127.0.0.1
```

и выполните:

```bat
openssl req -x509 -nodes -newkey rsa:2048 -sha256 -days 1826 ^
    -keyout ServerPrivateKey.pem -out ServerCertificate.pem -config cert.cnf
```

В разделе `[san]` замените `SCADA-HOST` именем компьютера и перечислите
идентификаторы (ApplicationUri) всех процессов, работающих на нем:
`urn:telecontrol:scada:server` для `scada-config` и `scada-proxy`,
`urn:<имя компьютера>:scada:<процесс>` для остальных (например
`urn:SCADA-HOST:scada:iec104`). Спецификация OPC UA требует, чтобы сертификат
содержал идентификатор приложения, и процессы Сервера это проверяют, как и
сторонние клиенты OPC UA. **Самоподписанную пару остальные процессы не
принимают**: свою пару должен выдать удостоверяющий центр объекта или центр,
сертификат которого вы положили в папку `issuer` на каждом компьютере
объекта.
Скопируйте оба файла в папку, на которую ссылаются параметры, и ограничьте
доступ к файлу ключа учетной записью SYSTEM и администраторами (группы
заданы идентификаторами, поэтому команда работает в Windows на любом языке):

```bat
icacls "C:\Program Files\Telecontrol SCADA\data\Certificates\ServerPrivateKey.pem" /inheritance:r /grant:r *S-1-5-18:F *S-1-5-32-544:F
```

**Сертификаты клиентов.** В установке, созданной `scada-setup`, каждый
процесс, кроме `scada-config`, принимает в защищенных соединениях только
сертификаты, выданные удостоверяющим центром объекта или перенесенные в
папку `trusted`: его блок `opcua` ссылается на папки `issuer`, `trusted` и
`rejected` в `data\Certificates`. `scada-config` принимает любой клиентский
сертификат, потому что подключаемый к объекту компьютер обращается к нему,
еще не имея своего сертификата; все, что предоставляет `scada-config`,
требует входа под учетной записью, а сертификат объекта он выдает только
учетной записи `svc`. Регистрацию процесса `scada-config` и `scada-proxy`
принимают только по соединению с сертификатом, выданным удостоверяющим
центром объекта (блок `opcua.register_trust` ссылается на папку `issuer`, а не
`trusted`), и только под идентификатором (ApplicationUri), указанным в этом
сертификате. Папки такие:

| Параметр | Описание |
|---|---|
| `trusted_certificates_dir` | Доверенные сертификаты клиентов (PEM или DER); клиент принимается, если его сертификат есть в этой папке |
| `issuer_certificates_dir` | Сертификаты удостоверяющих центров; принимается клиент, чей сертификат ими подписан |
| `crl_dir` | Списки отзыва для удостоверяющих центров |
| `rejected_certificates_dir` | Сюда записываются отклоненные сертификаты клиентов — их можно перенести в доверенные |

Дополнительные ограничения задаются в блоке `opcua.security`:
`"allow_none": false` запрещает незащищенные соединения,
`"require_encryption_for_password": true` запрещает передачу пароля без
шифрования, `"require_trusted_client_cert": true` не дает процессу запуститься
без папки доверенных сертификатов, `"allow_anonymous": false` запрещает
анонимный вход (по умолчанию он разрешен).
Настольный Клиент при входе типа «Телеконтроль» (порт TCP 2000) сертификат
Сервера не проверяет; при входе типа «OPC UA» в режимах «Максимальная
безопасность» и «Подпись и шифрование» — проверяет и при первом подключении просит подтвердить доверие к нему (смотрите
[Проверка сертификата Сервера]({{ '/getting-started/' | relative_url }}#server-certificate-check)).

`scada-setup` задает их сам: `"allow_none": false`, `"allow_anonymous":
false` и `"require_encryption_for_password": true` у всех процессов; с
`--allow-anonymous-opcua` у `scada-proxy` — `"allow_none": true` и
`"allow_anonymous": true`.

**ВНИМАНИЕ:** в установке с `--insecure-links` процессы подключаются друг к
другу без защиты и передают пароль `svc` без шифрования, поэтому там
**`"allow_none": false` и `"require_encryption_for_password": true`
разрывают связь между процессами**.

### Удостоверяющий центр объекта {#opcua-site-ca}

Процессы доверяют друг другу потому, что все их сертификаты выдал один
удостоверяющий центр — собственный центр объекта на центральном компьютере.

* **Центральный компьютер** (тот, где работает `scada-config`): первый
  `apply` создает удостоверяющий центр в
  `C:\Program Files\Telecontrol SCADA\data\Certificates\ca` и выдает от
  него сертификат самого компьютера. Затем он выводит строку, нужную
  остальным компьютерам:

  ```
  Links are encrypted (SignAndEncrypt). Join the other computers of the site with
    --central-fingerprint 30:CE:C4:DB:...:66:6F
  ('scada-setup status' prints it again)
  ```

  **Файл `ca_key.pem` — ключ, которым выдаются все сертификаты объекта.**
  Под Windows читать его могут только учетная запись SYSTEM и
  администраторы. Под Linux он принадлежит `root` и группе `scada` (права
  0640): его может прочитать любой процесс Сервера на центральном
  компьютере, поэтому не запускайте от имени учетной записи `scada` ничего,
  кроме служб Сервера. Сохраняйте
  его в резервной копии вместе с конфигурацией и никогда не копируйте на
  другой компьютер.
* **Каждый остальной компьютер**: передайте `apply` этот отпечаток в
  параметре `--central-fingerprint`. Тогда `apply`:
  1. проверяет, что сертификат центрального компьютера имеет этот отпечаток,
     и, если нет, останавливается, ничего не меняя, — так пароль `svc` не
     уходит другому компьютеру;
  2. входит в `scada-config` под учетной записью `svc`;
  3. создает ключ этого компьютера, который его никогда не покидает, и
     получает для него сертификат от удостоверяющего центра;
  4. записывает файлы параметров, в которых все соединения зашифрованы.

  Двоеточия и регистр букв в отпечатке значения не имеют. Каждый `apply` на
  центральном компьютере выводит его снова, а в любой момент его показывает
  [`scada-setup status`]({{ '/server/monitoring/' | relative_url }}#monitoring) на центральном компьютере (строка
  `Other computers join the site with --central-fingerprint …`); показывает
  его и [OpenSSL](https://www.openssl.org/):
  `openssl x509 -in ServerCertificate.pem -noout -fingerprint -sha256`.

  Отпечаток нужен только для подключения. Подключенный компьютер хранит
  сертификат удостоверяющего центра и в следующих `apply` проверяет
  сертификат центрального компьютера по нему, а не по отпечатку.

Если `apply` на остальном компьютере сообщает:

* `presented a certificate with fingerprint …, not the … given` — отпечаток
  введен с ошибкой, `--central` указывает на другой компьютер или на
  центральном компьютере с тех пор новый удостоверяющий центр, а отпечаток
  указан прежний. Нынешний отпечаток выводит `scada-setup status` на
  центральном компьютере. Замена только сертификата центрального компьютера
  к этой ошибке не приводит (смотрите
  [Отпечаток центрального компьютера изменился](#central-fingerprint-changed)).
* `presents a certificate (fingerprint …) that the site CA this computer holds
  did not issue` — компьютер уже подключен, а центральный компьютер с тех пор
  получил новый удостоверяющий центр (или `--central` указывает на другой
  компьютер). Выполните `apply` с `--central-fingerprint` и отпечатком,
  который выводит `scada-setup status` на центральном компьютере.
* `cannot sign in to scada-config … as svc` — пароль `svc` отличается от
  пароля центрального компьютера. **После пяти неудачных входов
  `scada-config` 15 минут отказывает этому компьютеру** даже с правильным
  паролем.
* `the central computer's certificate does not name the address` — остальные
  компьютеры обращаются к центральному по адресу, которого нет в его
  сертификате. Укажите в `--central` имя центрального компьютера или на
  центральном компьютере удалите `ServerCertificate.pem` и
  `ServerPrivateKey.pem` и снова выполните `apply` с `--advertise` и этим
  адресом.

**Объекты, установленные до этой версии,** переходят сами:

1. Выполните `apply` на центральном компьютере. Он создает удостоверяющий
   центр и заменяет самоподписанную пару.
2. Выполните `apply` с `--central-fingerprint` на каждом остальном
   компьютере.

Пока компьютер не переведен, его соединения с переведенными компьютерами не
работают, поэтому переводите все компьютеры за один сеанс.

#### Срок действия и новый удостоверяющий центр {#opcua-renewal}

Сертификат компьютера действует 5 лет, сертификат удостоверяющего центра
объекта — 10 лет с момента создания. Когда истекает сертификат компьютера,
остальные процессы перестают принимать его соединения, и его устройства
пропадают из Клиента; когда истекает сертификат удостоверяющего центра — то же
происходит со всеми компьютерами объекта. Даты начала и окончания показывает
[`scada-setup status`]({{ '/server/monitoring/' | relative_url }}#monitoring): строка `Valid from … to …` под
`OPC UA certificate` — для сертификата компьютера, под `Site CA` на
центральном компьютере — для удостоверяющего центра. Их же показывает
[OpenSSL](https://www.openssl.org/):
`openssl x509 -in ServerCertificate.pem -noout -enddate` (для центра —
`ca\ca.pem` на центральном компьютере). Заменяйте сертификаты заранее.

`apply` не заменяет действующий сертификат, выданный удостоверяющим центром,
которому доверяет этот компьютер, — даже если срок его скоро истекает.
Поэтому:

* **чтобы обновить сертификат компьютера**, остановите на нем процессы
  (`scada-setup stop`), удалите файлы `ServerCertificate.pem` и
  `ServerPrivateKey.pem` из папки `data\Certificates` в папке установки
  (`C:\Program Files\Telecontrol SCADA\data\Certificates`, под Linux —
  `/opt/telecontrol-scada/data/Certificates`) и выполните `apply` с
  [параметрами компьютера]({{ '/server/setup/' | relative_url }}#scada-setup-options) — на подключенном
  компьютере без `scada-config` вместе с `--svc-password`: новый сертификат
  он получает от `scada-config`, отпечаток для этого не нужен. После
  обновления сертификата самого центрального компьютера его отпечаток
  меняется, но остальные компьютеры узнают его по удостоверяющему центру, и
  на них менять ничего не нужно (смотрите
  [Отпечаток центрального компьютера изменился](#central-fingerprint-changed));
* **новый удостоверяющий центр** появляется, если на центральном компьютере
  удалить подпапку `ca` (чтобы заменить истекающий центр) или если ее
  потеряли — например, при удалении программы с
  `SCADA_PURGE_CERTIFICATES=1` или при восстановлении без этой папки. Тогда
  сертификаты всех компьютеров выданы прежним центром, и **каждый остальной
  компьютер нужно подключить заново**. На самом центральном компьютере
  `apply` заменяет при этом и его собственную пару: прежняя откладывается
  рядом с расширением `.previous-ca`, а отпечаток центрального компьютера
  меняется — новый выводят этот же `apply` и `scada-setup status`. Это
  единственный случай, когда новый отпечаток нужен на остальных компьютерах:
  на каждом из них выполните `apply` с
  [параметрами компьютера]({{ '/server/setup/' | relative_url }}#scada-setup-options) и новым отпечатком в
  `--central-fingerprint`. `apply` сам
  заметит, что сертификат этого компьютера выдан не нынешним центром,
  отложит прежнюю пару рядом с расширением `.previous-ca` и получит новую;
  удалять файлы сертификата вручную не нужно. Пока компьютер не подключен
  заново, его соединения не работают, поэтому подключайте все компьютеры за
  один сеанс.

#### Отпечаток центрального компьютера изменился {#central-fingerprint-changed}

Отпечаток центрального компьютера меняется вместе с его сертификатом:

* после [обновления сертификата](#opcua-renewal) центрального компьютера;
* после переустановки программы на центральном компьютере (установщик
  удаляет его сертификат) или восстановления его под другим именем;
* после того как его пару создали заново для `--advertise`;
* после замены удостоверяющего центра объекта;
* после того как `apply` добавил на центральный компьютер процесс: компьютер
  получает новый сертификат, в котором указан и этот процесс.

**Если удостоверяющий центр прежний, на остальных компьютерах ничего менять
не нужно.** Подключенный компьютер проверяет сертификат центрального
компьютера по удостоверяющему центру, а не по отпечатку, поэтому его `apply`
(в том числе при обновлении и восстановлении) работает и с прежним
отпечатком в `--central-fingerprint`, и без него; подключать такие компьютеры
заново не нужно. Новый отпечаток понадобится только для подключения новых
компьютеров — его выводят `apply` и `scada-setup status` на центральном
компьютере.

**Если удостоверяющий центр новый**, остальные компьютеры нужно подключить
заново с новым отпечатком (смотрите
[Срок действия и новый удостоверяющий центр](#opcua-renewal)). Пока этого не
сделано, `apply` на них завершается сообщением `presented a certificate with
fingerprint …, not the … given` (с прежним отпечатком) или `… that the site CA
this computer holds did not issue` (без отпечатка) и ничего не меняет.

Чтобы заметить новый удостоверяющий центр, `apply` на подключенном компьютере
обращается к `scada-config` на центральном компьютере. Если тот недоступен,
`apply` выводит предупреждение `could not check the central computer's site
CA`, оставляет сертификат этого компьютера и продолжает работу. Если
удостоверяющий центр могли заменить, выполните `apply` еще раз, когда
центральный компьютер заработает.

## Клиент OPC (Windows) {#opc-classic}

На Windows Сервер может подключаться к внешним OPC-серверам по протоколу OPC DA (Classic OPC). При включении этой функции теги внешних OPC-серверов отображаются в адресном пространстве Сервера ОИК и могут быть привязаны к объектам.

```json
"opc": {
    "client": {
        "enabled": true
    }
}
```

Функция доступна только на Windows.

## Интеграция с ОИК Видикон {#vidicon}

Сервер поддерживает интеграцию с системой ОИК Видикон для миграции существующих проектов. При включении Сервер импортирует объекты из конфигурации Видикон в своё адресное пространство.

```json
"vidicon": {
    "enabled": true
}
```

Функция доступна только на Windows.
